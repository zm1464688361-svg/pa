# 单题全量检查表

读取范围：教师共同要求、本题完整题面、补充要求、提交规范。下列为不得漏查的分类，**不能代替题面逐条展开**。为每个原子要求建立 R 编号，列出来源、角色、前置、输入、动作、预期状态、金额/资源/权限影响、最终证据。每条只能有一个计分归属；拆分、赋权在查看学生结果前完成。

## 证据判定

- `pass`：适用要求完全满足，有相符版本的可核查证据。
- `partial`：仅部分完成，指出已完成和未完成范围；仍未完全合规。
- `fail`：存在相反证据，或已全面定位检查后确认没有该必交成果；必须给出位置或搜索范围。
- `unknown`：材料缺失、权限限制、无法播放/运行、版本不明或证据冲突，不能确认；不等同于已证实没做。
- `na`：题面存在明确条件且条件未触发，提供条件和证据。必交成果、无法取证、环境缺失不能列为 na。

证据统一用 E 编号，记录：类型、源路径/URL、行号/消息 ID/视频时间点、提交版本、事件时间及时区、精简引文或命令及退出码、支持/反驳什么结论。引文不泄露密钥；群截图应脱敏。学生摘要与 Agent 自述是线索，须向源码、原始执行、平台记录或实际演示交叉核查。冲突证据并列，不自动选择有利或不利一方。

## A：先验收成果

| 分类 | 全量检查范围 | 判定重点 |
| --- | --- | --- |
| A1 业务 | 各角色、每条规则、每组工作场景的全部分支、异常/人工处理、业务收尾 | 是否真实可执行；不是仅完成主路径、接口数量或页面数量 |
| A2 数据与权限 | 数据库落库、初始化、重启、金额/数量/配额、时间、状态、并发、幂等、权限、外部模拟边界 | 规则是否同时成立；敏感信息和越权影响；相关持久化证据 |
| A3 验证质量 | 单元原件、包清单、整体和核心包覆盖率、排除规则、测试断言、格式/vet/竞争检测、接口集成、缺陷复测 | 整体及各核心包均 ≥85%；不是截图达标或只验证 mock；未纳入 profile 的自编包不能消失 |
| A4 交付 | 初始化与运行说明、实际流水线、部署地址与制品/提交、上线业务冒烟、恢复办法、视频完整效果、当日群提交 | Dockerfile 不等于自动部署；健康接口不等于业务完成；视频和运行版本可对应 |

运行先检查命令来源和副作用，限隔离副本。使用现有真实测试并补充教师验收探测，补充探测与学生原测试分开，不修改学生产物。记录环境条件与失败性质，服务不可访问须核查访问条件后再判定，不冒称业务实现失败。

覆盖率：明确生产代码与核心包清单，核查 profile 与实际单元执行命令；只显示已测包的 90% 不能证明全体 85%。生成/第三方排除须符合题面，自编 HTTP/DAO 等不得任意排除；一个核心包 80% 即使整体 95% 仍不合规。题目允许模拟上游，不因此减分；核心业务只模拟成功结果则不能得实际完成分。

视频：实际查看内容和效果，与时间目录逐项核对，语音讲解、角色切换、分支和异常均不可省。只有转写可审查讲解覆盖，不能确认画面效果、实际操作或是否借用他人；不凭口音或风格推断身份。不能播放时列待补证。

## B：再核对开发过程

### B1 阶段与交接

必须核对实际发生顺序：MCP 建仓、准备并加载 Agent 约束 → 需求分析 → 原型 → 任务计划 → Agent 开发 → 独立 Agent 测试 → 独立 Agent 验收 → 合规 PR 合并 → 主分支门禁与部署 → Skill 总结、视频和当日群交付。

允许计划迭代、局部测试伴随开发、测试失败返回修复、验收失败返回需求或实现；不强制瀑布式一次完成。必须存在进入下一阶段的有效前置和最终独立测试/验收。一个长会话仅改角色称呼不代表上下文独立。首次实现早于需求/原型/计划的相反证据要如实列出；未发现早期记录只说明不可证明，不能仅看最后文件时间断定倒序。

### B2 AI 指令与使用

- 自编 `AGENTS.md` 针对项目，包括职责/改动范围、规则来源、授权、Git、质量、数据与失败处理；检查实际加载时间、约束变化、违反时学生是否纠正。
- 全部可见提示词、AI 回复、工具、结果、重试和附件可追溯；Markdown 与事件清单对应，分会话导出要有关联索引。平台不提供的字段标记不可获取。
- 全部关键业务任务都有实现及验证链；任务清单已完成却无对应实现/验证记录必须指出。
- 查业务假设、API 用法、越界改动、泄密、错误解释、未经核验的“完成”、忽略失败、弱化测试、跳过独立检查和部署顺序。按证据批评行为，不给“AI 使用越多越好”的结论。

### B3 Skill

- 至少两个自编：业务专项、验收检查；核对自编内容、版本、业务适配、配置和实际调用。
- 每个具备用途、触发、输入、步骤、输出、失败处理、完成标准。
- 全部使用过的自编/改编/既有 Skill 汇总，逐个说明来源、使用位置、原因、过程、实际帮助、证据与局限。
- 有发现问题时核对修正及复检；无发现时检查范围及依据，不要求学生编造缺陷。
- 仅有通用角色提示、未实际使用的 Skill 或完工后补写调用不能算满足。

### B4 Git 与提交

- 每人每题独立仓库、开发前 GitHub MCP 创建证据，普通仓库截图不能证明 MCP 创建。
- 仅初始空仓库 README 等允许初始化主分支；业务、测试、文档、Skill、配置都在 `dev/<题号>`。
- 分阶段真实历史；没有工具/PR/事件证据时不能用 Git 提交图单独证明没有直推。审计当前规则还要核对关键时期生效记录，当前补开保护不证明此前受保护。
- 原附件类型 `feat/fix/hotfix/opt/docs/test`，方括号格式、中文描述、版本及编号必填规则、一提交一类型；不套用个人 `<type>(scope)`。
- `feat/fix` 提交前 meegle CLI 实际核验项目 `r17te9` 下真实且相关工作项。原始失败、确认和最终成功均保留；编号仅匹配正则不算有效核验，普通缺陷不能滥用 hotfix 绕过。
- 功能/单元/覆盖率/相关并发及独立验收通过才发起 PR，PR 状态检查通过才合并；实际主分支禁止直推/删除/强推且要求 PR 和指定检查。
- 合并后主分支新哈希重新门禁构建部署；源提交、PR、合并提交、制品、视频和上线可关联。合并生成哈希差异本身不违规。

## 本次每日交付

只确认本题学生在指定北京时间业务日的完成与群提交，说明提交时间、所交版本及材料齐全度。不用一道题证明连续二十天达标。讲解须按业务与开发思路覆盖共同要求和本题全部场景，Skill 帮助说明要具体。由学生或教师提供群记录，检查 Skill 不代发群消息。

## 覆盖率与完成度的区别

报告同时输出：业务要求完全通过数/适用业务要求数、全部必做要求完全通过数/适用必做数、partial/fail/unknown 各数量，以及 10 分得分。计数比例不能用“部分”冒充全部；分项权重和分数不能取代全量合规矩阵。
