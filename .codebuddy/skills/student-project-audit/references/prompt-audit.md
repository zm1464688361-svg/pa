# 提示词完整步骤与不合理 AI 操作检查

## 建立完整时间链

通读全部可见记录，按会话和时间排序，保留原记录编号。统一到北京时间但保留原始时区；Git 作者时间、提交时间、文件时间、平台事件及用户整理时间分别标注，不互相替代。核对消息缺页、附件缺失、会话未导出、工具结果空白及事件清单断点。不能因学生声称“已导出全部”跳过完整性核查。

按照下表逐阶段列出实际步骤，任务实现部分还须展开到本题每个业务分支：

| 阶段 | 应能找到的完整实现步骤/证据 |
| --- | --- |
| 准备 | 指定题面与交付范围；GitHub MCP 建仓；开发分支；自编 Agent 约束创建及加载；环境和权限确认 |
| 需求 | AI 读取完整题面；识别角色、规则、状态、异常与边界；学生解决歧义或记录合理假设；输出可验证条件 |
| 原型 | 根据角色设计页面及正常/异常状态；学生检查原型是否覆盖业务；产物及对应版本 |
| 规划 | 任务与需求关联；依赖及顺序；每项实现、测试、验收和部署完成条件；确认范围 |
| 开发 | 每项任务输入上下文与约束；相关 Skill 真实触发；代码实际变更；必要接口依据；AI 输出及学生检查 |
| 任务实现明细 | 为每条业务分支列具体操作顺序、对应提示、工具/代码结果、持久化及权限/异常处理、验证依据；不能只写“实现订单模块” |
| 测试 | 独立测试上下文收到原题与版本；正常/边界/失败/并发/权限用例；实际执行结果；单元整体及包覆盖率；缺陷与修复复测 |
| 验收 | 独立验收上下文；逐规则及完整场景检查；实际证据、未解决项；验收后改动重新检查 |
| Git 合并 | 原规范消息；提交前真实编号核验；开发分支测试和验收通过；PR、规则及状态检查；合并来源与最终版本 |
| 上线 | 主分支实际提交复验；实际构建及部署；健康和业务检查；失败恢复；服务版本 |
| 总结交付 | Agent 约束与所有 Skill 的实际使用和帮助说明；完整可见会话及事件索引；学生讲解效果视频；当日群记录 |

每条明细至少包含：`步骤编号、需求/任务号、前置步骤、应做动作、实际提示位置、AI行动、工具实际结果、学生判断、产物/版本、后续验证、状态、证据、缺口及补正思路`。

对每个业务实现任务，必须按实际发生顺序补出可核查的步骤清单，例如角色动作、输入校验、状态或资源变化、异常处理、持久化、后续查询核查及测试；这里是检查学生有无实现，不替学生设计完整答案。每步分别关联提示、代码/工具和验证证据，缺少的步骤逐条列明。

提示可以引用已加载的题面、约束或任务上下文，也可以一条覆盖多个步骤，只要引用内容可定位。AI 已在一个明确授权任务中自主实现并实际验证的步骤，不因缺少人工逐行指令扣分；相反，提示词写得很完整但没有实际执行也不算完成。

区分三种情况：

1. **步骤明确跳过**：原始记录显示从前一环节直接推进，且有相反代码/平台证据，例如明确要求跳过测试后合并。列已证实违规。
2. **记录不完整**：摘要写“已测试”，但缺调用、结果或对应版本。列缺失步骤证据，判 unknown，不擅自断言没有测试。
3. **合理循环**：测试暴露规则问题 → 学生核实 → 修改需求、任务和实现 → 重测验收。只要前置与最终门禁成立，不因阶段重复判倒序。

## 判断 AI 操作是否合理

检查每个关键决策是否给 AI 提供必要背景、适当权限和可执行完成标准，是否对结果核验，失败后是否正确诊断。评价能否实现题面及遵守本项目约束，不要求逐字套用某种提示词模板。

| 实际证据显示的行为 | 应说明的问题 | 正确思路与修正方向 |
| --- | --- | --- |
| 只让 AI “把题做完”，既未加载题面也无规则，直接接受输出 | 需求和约束缺失，验收无依据 | 先加载完整题面及业务角色规则，列任务与验收条件，再逐任务实现和核验 |
| AI 增加未约定业务规则，学生未核查即上线 | 擅自改变需求，可能偏离题意 | 回到教师规则确认；记录假设与影响，修正相关实现及测试 |
| 测试失败后指令删除测试或降低断言，让覆盖率达标 | 以数字绕过质量门禁 | 保存失败证据，定位生产行为或错误用例原因，修复并重新运行真实断言 |
| AI 声称通过，学生未查看工具输出就合并 | 未核验完成声明 | 绑定最终版本执行功能、单元和验收，确认结果后再 PR 合并 |
| 在同一上下文里称“现在你是验收 Agent”而没有独立检查 | 缺少题面要求的独立验收 | 新建独立任务上下文，提供原题、交付版本和客观材料重新验收 |
| 未核验编号、直接推主分支或先上线后补报告 | 违反提交及阶段门禁 | 在开发分支关联真实工作项，按门禁 PR 合并；补验当前版本并保留历史违规 |
| Skill 只有文件没有调用，最后补写帮助总结 | 不能证明 Skill 实际发挥作用 | 在实际任务触发并保留输入输出、修正与验证；事后补做标明复查，不伪装原过程 |
| 原始记录与终版报告冲突，或视频/报告版本不同 | 结论真实性或适用版本存疑 | 并列冲突证据，查平台/原始产物与时间线，不能直接指控造假 |

上述表只在出现相应证据时使用，不能把它当作学生已发生的问题。所有问题条目须包含：

- `问题编号、原始位置/时间、最短必要引文或动作、关联约束、证据编号`。
- `已证实影响`与`潜在风险`分别陈述，不能将风险写成已发生损失。
- 正确思路、可执行修正步骤、需要的输入与权限、预期输出及复验条件。
- 数值失分归属、涉及的必做门禁和历史是否可补证；不重复扣同一原子项。

单个教学例：会话 M42 写“删掉余额不足测试再提交”，工具输出显示该断言已删且 PR 随后合并。应引用 M42、对应 diff 和 PR 时间，指出弱化测试及带缺陷合并；建议恢复有依据的断言、定位余额行为、修复重测并重新验收。不得仅写“提示词不专业”，也不要求检查者给出本题完整实现答案。

## 缺失步骤必须逐条输出

对每条缺口写：应处阶段及前置、已覆盖部分、缺失动作或证据、为什么影响验收、补交或重做方式、复验方法。历史执行无法补造；现在重跑测试能证明当前结果，不能证明当时合并前已测试。教师提供真实历史证据后才可修正历史结论。
